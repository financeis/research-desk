# 업무 규칙

## 용어

| 용어 | 뜻 |
|---|---|
| 리포트 = 보고서 | 같은 말이다. 텔레그램 메시지 하나에 붙은 PDF 하나가 `reports` 표의 한 행이다 |
| 분류(태깅) | 리포트 행에 종류·발행처·종목·분석 대상 여부 같은 메타데이터를 붙이는 일. `tag` 명령이 한다 |
| 분석 | 사용자가 고른 단일종목 리포트 1건에서 재무 정보를 뽑는 일. 분류와 다른 것이다. 결과는 `report_summaries` 표에 간다 |
| 분석 대상 외(OOS) | 분석 범위 밖으로 분류된 행. `out_of_scope_reason`이 채워져 있다 |
| 분석 대상 | `tagging_status ∈ {auto, verified}`이고 `out_of_scope_reason IS NULL`인 행 |
| 산업 / 섹터 | 산업은 산업명(대) 단위의 넓은 리포트, 섹터는 좁은 테마 리포트(종목 0~N개) |
| 발행처 | 리포트를 낸 곳. 발행처 사전(`research_desk/tagger/vocabulary/publishers.yaml`)의 정식 이름으로 저장한다. IR자료의 발행 주체는 그 기업 자신이다(`해당기업`) |
| 파일 이름 표기 | 채널이 파일 이름 끝에 붙이는 증권사 표기. `…_YYYYMMDD_<표기>_<숫자>.pdf`의 `<표기>`(예: `MERITZ`). 발행처를 의심할 때만 쓴다 |
| 종목표 | KRX 상장 종목 CSV(`docs/stock_data/KRX_stocks_data.csv`). 코드·이름·시장·산업명(대·중)·주요 제품 |
| 종목표 버전 | `reports.taxonomy_version`에 저장되는 `KRX@<자료 기준일>`. 리포트 분류 체계(종류·사유 목록)의 버전이 아니다 |
| 분류 체계 | 리포트 종류·분석 대상 외 사유·발행처 종류·분류 상태·신뢰도의 값 목록. 버전이 없다. 값이 바뀌면 DB 제약도 함께 바뀌어야 한다 |
| 커버리지 숫자 / 리포트 수 | 둘 다 리포트 행을 세지만 다른 숫자다. 커버리지 화면의 숫자는 "이 채널에서 다뤄진 횟수"(그 종목을 담은 모든 분석 대상 행)다. 유사 기업 화면의 리포트 수는 종목 리포트·섹터 언급·기타 리서치로 나눈 최근 365일 숫자이고, 사용자가 "이 채널에 국내 증권사 리포트가 거의 다 올라온다"고 확인해서 종목 리포트 수를 증권사 커버리지로 쓴다 |
| 시드 / 피어 | 시드는 유사 기업을 찾는 기준 회사(기업 화면에서 연 회사), 피어는 시드와 사업이 비슷한 회사 |
| 프로필 | AI가 사업보고서로 만든 회사별 사업 요약 카드. (회계연도, 프로필 버전, 종목코드)마다 하나 |
| 사업부문(부문) | 프로필 안의 사업부문. 이름·제품·키워드·매출 비중(원문 표에 없으면 -1 = 비중 미상)을 가진다 |
| 빌드 / 공개 빌드 | 빌드는 한 회계연도 프로필 묶음의 임베딩·백분위표·용어표를 계산하는 한 회분((회계연도, 프로필 버전, 임베딩 모델)마다). 공개 빌드는 상태가 `done`인 빌드이고, 화면은 가장 최근 공개 빌드만 쓴다 |
| 비교 열쇠 | 용어를 비교하는 정규화 값. 동의어표의 표준 표기로 바꾼 뒤 대소문자·공백·가운뎃점·하이픈을 무시한다 |
| 초과수익률 | 기간 수익률 − 같은 실행·같은 시장 종목들의 그 기간 수익률 중앙값(%p). 지수 대비가 아니다 |
| 후보 | 아래 "후보"의 여섯 조건을 모두 만족해 화면에서 강조하는 피어 |
| 수급 / 순매수 | 투자자 구분(주체)별로 그날 산 금액 − 판 금액(순매수 거래대금). KIS가 백만 원 단위로 준다. 0보다 작으면 순매도다 |
| 주체 | 수급을 나누는 KRX 투자자 구분 11개: 사모·외국인·기관합계·연기금·투신·금융투자·보험·은행·기타금융·기타법인·개인 |
| 250일 순위 | 그날 순매수가 그 종목의 최근 250거래일(그날 포함) 가운데 몇 번째로 큰지. 그날보다 큰 날의 수 + 1 |
| 순위 매긴 날 | 수급 갱신이 순위를 매겨 날 목록에 올린 거래일. 그날 주가 갱신이 받은 실제 시총이 있는 날만 오른다. 수급 랭킹 화면은 이 날들만 보여 준다 |

## 리포트 행

- **한 행의 정체.** `(chat_username, message_id)`가 같은 행은 하나뿐이다(DB 고유 제약). 같은 PDF가 다른 메시지로 다시 올라오면 별도 행이 된다. `file_hash_sha256`이 저장되지만 같은 내용의 행을 묶지 않는다. 그래서 같은 PDF가 두 번 들어오면 목록·커버리지에 두 번 센다.
- **수집 때 채우는 값.** 메시지 번호, 채널 라벨(`TELEGRAM_CHANNEL` 값), 보낸 시각(`sent_at`, UTC), 파일 이름, 저장 경로(`file_path`, 저장 폴더 기준 상대 경로), 크기, SHA-256, 캡션. 새 행의 `tagging_status`는 `pending`이다.
- **분류 때 채우는 값.** 발행일, 리포트 종류, 발행처, 발행처 종류, 애널리스트, 제목, 종목 코드·회사명(종목표로 맞춘 값 `stock_codes`·`company_names`와 원문 값 `stock_codes_raw`·`company_names_raw`), 업종(대·중), 주요 제품, 분석 대상 외 사유, 분류 상태, 신뢰도, 메모(`tagging_notes`), 분류 시각, `tagger_version`, `taxonomy_version`.
- **행을 지우면.** 그 행의 분석 결과(`report_summaries`)도 같이 지워진다. 다른 분석 결과가 이 행을 앞 문서로 가리키던 비교 기록은 `prev_report_id`만 비워지고 남는다.

## 분류 상태 전이

| 시작 → 결과 | 조건 |
|---|---|
| (수집) → `pending` | 새 행 |
| `pending` → `processing` | 작업자가 가져감. `tagging_locked_at`과 `tagging_worker_id`를 기록한다. 가져가기는 `FOR UPDATE SKIP LOCKED`라 같은 행을 두 작업자가 동시에 가져가지 못한다 |
| `processing` → `auto` 또는 `review_needed` | 행 하나의 분류가 끝남 |
| `processing` → `pending` | 일시 오류(LLM 429·5xx·시간 초과·네트워크, 응답 형식 오류), 행 처리 시간 한도(`PER_ROW_DEADLINE_S`, 기본 90초) 초과, 예기치 못한 오류 — 정상 실행 모드에서만. 또는 잠금이 `LOCK_TTL_MINUTES`(기본 30분)보다 오래 묵음. 또는 같은 작업자 ID 단위 되돌리기(`tag reset-worker`) |
| `review_needed` → `verified` | 수동 승인 |
| `review_needed` → `verified` + 분석 대상 외 | 수동 제외. 사유 5개 중 하나가 반드시 있어야 한다 |
| `review_needed` → `pending` | 수동 재분류. 분류 칸 전부를 비운다. `report_summaries`는 건드리지 않는다 |
| `verified` 또는 `pending` → `review_needed` | 수동 처리의 되돌리기. 처리 뒤 행이 그대로일 때만 된다 |
| `review_needed` → (재처리 모델로 다시 분류) | `tag escalate --since <시각>`. 상태를 다시 확인하지 않고 덮어쓴다 |
| `auto` 또는 `review_needed` → `pending` | 다시 분류 대기(`tag requeue --apply`). 고른 조건에 맞는 행을 백업한 뒤 한 트랜잭션에서 수동 재분류와 같은 모양으로 되돌린다. `verified`·`processing`·`pending` 행은 고르지 않는다. 다음 백필이 지금 규칙으로 다시 분류한다 |

- `review_needed`가 되는 행의 신뢰도는 언제나 `low`다.
- 정상 분류(`tag run`)는 `pending` 행만 가져간다. 이미 분류된 행이 다시 분류되는 길은 넷이다: `tag requeue`(조건에 맞는 `auto`·`review_needed` 행을 `pending`으로 되돌림, 다시 분류는 평소 백필), 검토의 재분류(`review_needed` 한 건), `tag escalate`(`review_needed`를 재처리 모델로), `tag run --row-ids 1,2,3`(상태와 상관없이 지정한 행, 가져가기 표시 없이 쓰므로 동시에 도는 작업자와 겹칠 수 있다). 사람이 승인한 `verified` 행은 `--row-ids` 말고는 다시 분류되지 않는다.
- `auto` 행은 검토 대기열에 나오지 않는다. 조건으로 고를 수 있으면 `tag requeue`로, 한 건씩 고르면 `--row-ids`로 다시 분류한다. 사람이 값(발행처 등)을 직접 고르는 화면은 아직 없다.
- 다시 분류 대기로 되돌린 행은 다시 분류될 때까지 분석 대상이 아니어서 웹 목록에서 빠진다. 가져가는 순서가 `downloaded_at` 오름차순이라 새로 수집한 리포트보다 먼저 다시 분류된다.
- 오래 묵은 잠금은 정상 `tag run`이 시작할 때만 되돌린다. 계속 감시하는 장치는 없다. 잠금 시각은 가져갈 때 배치 전체에 한 번 찍히고, 동시 처리 자리를 기다리는 행도 그동안 `processing`이다. 그래서 `LOCK_TTL_MINUTES × 60`이 배치 하나의 최장 시간(⌈배치 크기 ÷ 동시 처리 수⌉ × `PER_ROW_DEADLINE_S`, 기본값이면 5 × 90초 = 7.5분)보다 길어야 한다. 짧으면 아직 도는 배치의 기다리는 행을 다른 실행이 되돌려 다시 가져가고, 같은 행이 두 번 분류된다.
- 분류 명령이 준비 문제(설정 누락, codex CLI 없음, 종목표를 못 읽음, 종목표 버전 불일치)로 끝날 때는 어떤 행도 `processing`으로 바꾸지 않은 상태여야 한다. `tag requeue`가 준비 문제로 끝날 때도 어떤 행도 바꾸지 않은 상태다.

## 분류 규칙

### 리포트 종류 6가지 (`report_type`)
- `단일종목`: 상장사 하나를 분석한 리포트. 상장 예정 종목 포함.
- `산업`: 산업(대) 단위.
- `섹터`: 좁은 테마. 종목 0~N개.
- `IR자료`: 발행 주체가 해당 기업 자신.
- `전략·시황`: 시황·매크로·퀀트·전략.
- `기타`.

### 분석 대상 외 사유 5가지 (`out_of_scope_reason`)
- `foreign`: 주된 대상이 해외 상장사.
- `fund`: ETF·펀드.
- `digital`: 디지털자산.
- `private`: 비상장. 비상장 신호가 있고 종목표에서도 코드를 못 찾을 때만 이 사유가 된다. 종목표에서 찾으면 비상장 신호가 있어도 분석 대상이다.
- `ir_self`: IR자료는 종류만으로 자동으로 이 사유다.

판정 순서: IR자료면 `ir_self`가 먼저다. 그다음 `foreign`·`fund`·`digital` 신호를 보고, 마지막으로 `private` 조건을 본다.

### 분석 대상 외 행 모양
분류기의 쓰기와 검토의 "제외" 처리가 똑같은 모양을 쓴다.
- 비우는 것: `published_at = NULL`. `stock_codes`·`company_names`·`sectors_major`·`sectors_minor`·`products`는 빈 배열.
- 그대로 두는 것: `report_type`, `publisher`, `publisher_type`, `analysts`, `title`, `stock_codes_raw`, `company_names_raw`.
- 넣는 것: `out_of_scope_reason`.
- 정해진 5개 밖의 사유는 받지 않는다(오류).

### `review_needed`가 되는 경우 4가지와 기본 메모
| 경우 | 기본 `tagging_notes` |
|---|---|
| 첫 쪽들에서 글자도 1쪽 그림도 얻지 못함, 또는 분류 모델이 그림을 받지 못함 | `first_page_unreadable` |
| LLM이 응답을 거부함(빈 답 포함) | `llm_refusal:<거부 내용>` |
| 단일종목인데 종목표에서 못 찾음(상장 예정이거나 종목표가 오래됨) | `krx_unmatched_in_scope:ipo_pending_or_unknown` |
| 종류가 `기타`이면서 LLM 자신감이 `low` | `type_indeterminate` |

산업·전략·시황은 종목표 매칭을 하지 않으므로 매칭이 없어도 `auto`다. 섹터는 매칭이 0개여도 `auto`다. 검토 사유는 이 4가지뿐이다(배치 보고의 `review_reasons`도 이 4가지 이름만 센다).

### 덧붙는 메모 (상태를 바꾸지 않는다)
| 경우 | 덧붙는 메모 |
|---|---|
| 1쪽 그림으로 AI에게 물어 읽은 행 | `page_image` |
| 파일 이름 표기가 가리키는 발행처가 있는데 저장한 발행처가 그것과 다름(비어 있음 포함) | `publisher_suspect:filename_mismatch` |
| 파일 이름 표기가 가리키는 발행처가 없고 저장한 발행처도 비어 있음 | `publisher_suspect:unknown` |

- 메모는 `;`로 잇고 순서는 기본 메모, `page_image`, `publisher_suspect:…`이다. 예: `krx_unmatched_in_scope:ipo_pending_or_unknown;page_image;publisher_suspect:unknown`. 그림으로 읽고 AI가 거부하면 `llm_refusal:<거부 내용>;page_image`다.
- 그림 행과 의심 행도 상태는 그대로다. `auto`면 검토 대기로 가지 않고 기업 화면에 바로 나온다. 신뢰도 `medium`과 메모로 나중에 골라 점검한다(일단 화면에 띄우고 애매한 것은 나중에 사람이 분류한다).
- 의심 표시는 AI 결과가 있는 행(분석 대상 외 포함)에만 붙는다. 못 읽음·거부 행에는 붙지 않는다. 분류 모델이 그림을 받지 못해 못 읽음이 된 행에도 덧붙는 메모가 없다.
- 이름 불일치 메모 `krx_name_code_mismatch`는 `auto` 행의 기본 메모다(아래 신뢰도).

### 신뢰도 (`tagging_confidence`)
- 분석 대상 `auto`: 기본 `high`. 다음 중 하나면 `medium`이다 — 발행일을 보낸 시각으로 대신 채움, 2쪽 이상 읽음, 단일종목에서 코드는 맞는데 원문 회사명이 종목표 이름과 다름(이때 메모 `krx_name_code_mismatch`).
- 분석 대상 외: 사유가 `private`일 때만 `medium`, 나머지 사유는 `high`.
- `review_needed`: 언제나 `low`.
- 마지막 규칙: 1쪽 그림으로 읽었거나(`page_image`) 발행처 의심 표시가 붙은 행은 `high`를 `medium`으로 낮춘다(`low`는 그대로). 그림으로 읽은 것은 발행일을 보낸 시각으로 채운 경우처럼 "대체 수단을 쓴 경우"로 본다.
- 그림도 의심도 없는 행의 상태·신뢰도·메모는 이 규칙이 생기기 전과 같다.

### 첫 쪽 읽기
1쪽부터 최대 3쪽까지 차례로 읽는다. 그때까지 읽은 글자에 표지 정보 신호(`분석가`, `애널리스트`, `투자의견`, `목표주가`, `리서치`, `증권`, `산업분석`, `시황`, `퀀트` 같은 고정 키워드 목록 중 하나)가 나오면 그 쪽에서 멈춘다. 신호가 없으면 3쪽까지 읽는다. 읽은 쪽이 2쪽 이상이면 신뢰도가 `medium`이 된다.

3쪽 안에 글자가 하나도 없을 때만(쪽 전체가 그림인 PDF) 1쪽을 그림(120dpi)으로 그려 AI에게 보여 준다. 시스템 프롬프트와 응답 모양은 글자 경로와 같고, 사용자 메시지에는 파일 이름·캡션·보낸 시각과, PDF 글자 대신 고정 문장 `(글자를 읽을 수 없는 PDF라 페이지를 그림으로 첨부했다. 첨부한 그림을 보고 추출한다.)`이 들어간다. 그 답은 글자로 읽은 행과 같은 갈래(거부 / 분석 대상 외 / 종목 매칭 → 상태 결정)로 가고, 메모 `page_image`와 신뢰도 상한 `medium`이 붙는다.
- 글자가 한 쪽에라도 조금이라도 있으면 그림을 쓰지 않는다(표지 정보가 부족해 3쪽까지 읽은 경우도). 비용을 최소로 하려는 선택이다.
- 그림이 AI 공급자 한도보다 크면 해상도를 낮춰 다시 그리고, 끝내 맞지 않으면 그림이 없는 것으로 친다.
- 그림도 못 만들면(파일 없음·깨짐·암호·0쪽·그리기 오류) AI를 부르지 않고 읽기 실패(`first_page_unreadable`)다. 분류 모델이 그림을 받지 못하는 모델이어도 같다(배치 보고의 `page_image_unsupported`로 센다).
- `--dry-run`, `--row-ids`, `tag escalate`도 같은 흐름이다.

### 종목 매핑 (리포트 종류별)
| 종류 | 방식 |
|---|---|
| 산업, 전략·시황 | 매핑하지 않는다. 종목 칸은 비어 있다 |
| 섹터 | 원문의 코드와 회사명으로 찾은 종목을 모두 모은다 |
| 단일종목, 기타 | 코드를 먼저 보고, 없으면 회사명으로 하나만 찾는다 |
| IR자료 | 분석 대상 외(`ir_self`)라 종목 칸을 비운다 |

- 분류기의 종목표 조회는 코드를 있는 그대로 찾는다(앞에 0을 채우지 않는다). 이름 조회는 공백·대소문자를 무시하고, 같은 이름이 둘이면 먼저 나온 행을 쓴다. 코드는 `^[0-9A-Z]{6}$`이면서 종목표에 있어야 유효하다.
- 웹에서 받은 종목 코드는 종목표 조회 때만 6자리가 되도록 앞을 0으로 채운다(기업 정보 표시, 관심 기업 존재 확인). DB 조회에는 받은 그대로 쓴다.

### 발행일
- LLM이 찾지 못하면 보낸 시각(`sent_at`)의 한국 날짜를 쓰고 신뢰도를 `medium`으로 낮춘다.

### 발행처
- **원본은 하나다.** 발행처 사전 `research_desk/tagger/vocabulary/publishers.yaml`이 발행처 이름의 유일한 원본이다. 항목마다 정식 이름(`canonical`)과 별칭(`aliases`: 옛 이름·영문 이름·약칭·파일 이름 표기)이 있고, 항목이 들어 있는 구역(`broker`/`data_provider`/`ir_agency`/`other`)이 발행처 종류다.
- **정식 이름 정하기.** 표지에 적힌 지금 회사명이다(한국어 정식 상호가 있으면 그것; 예: `DB증권`, `한국IR협의회`, `iM증권`, `에프앤가이드`, `한국거래소`). 증권사가 아닌 독립 리서치는 `data_provider`다. 기술분석보고서는 표지의 작성기관(한국기업평가·NICE신용평가·NICE평가정보·한국기술신용평가·서울평가정보 등)과 상관없이 `한국IR협의회`로 둔다(2026-10-10 사용자 결정). IR자료의 발행처는 `해당기업`(`other`)이다. 정식 이름은 서로 겹치지 않고, 별칭·표기 하나는 정식 이름 하나에만 대응하며 다른 항목의 정식 이름과도 같지 않다.
- **AI는 닫힌 목록에서 고른다.** 분류 프롬프트에 사전이 통째로 들어가고, AI는 정식 이름 하나 또는 "모름"(null)만 답할 수 있다(응답 모양이 정식 이름 목록으로 제한된다). 코드는 답이 정식 이름과 글자 그대로 같은지만 확인하고, 아니면(별칭, 오타, 엉뚱한 문장) 비워서 저장한다. 이 확인 때문에 행이 실패하거나 대기로 되돌려지는 일은 없다.
- **발행처 종류는 사전에서 온다.** 저장한 정식 이름의 구역이 종류이고, 발행처가 비면 종류도 비어 있다. AI는 종류를 내지 않는다.
- **판단은 AI다.** PDF 속 글자를 코드로 대조해 발행처를 정하지 않는다. 파일 이름 표기도 저장할 발행처를 정하지 않는다 — 의심 표시와 다시 분류 대상 고르기에만 쓴다.
- **파일 이름 표기와 의심 표시.** 파일 이름이 `_YYYYMMDD_<표기>_<숫자>.pdf`로 끝나고 그 표기가 사전의 정식 이름이나 별칭과 글자 그대로(대소문자까지) 같으면, 그 항목의 정식 이름이 "파일 이름이 가리키는 발행처"다. 사전에 없는 표기나 끝 모양이 다른 이름(예: 번호 뒤에 `_1`이 더 붙은 `…_<숫자>_1.pdf`)은 아무것도 가리키지 않는다. 가리키는 발행처와 저장한 발행처가 다르면(비어 있음 포함) `publisher_suspect:filename_mismatch`, 가리키는 발행처가 없고 저장한 발행처도 비면 `publisher_suspect:unknown`이 붙는다. AI가 별칭(예: `Eugene`)을 답하면 비워서 저장되고, 표기가 있으면 `filename_mismatch`, 없으면 `unknown`이다. 파일 이름 표기와 AI 답이 같으면 의심 표시가 없다. IR자료(`해당기업`)가 증권사 표기 파일이면 `filename_mismatch`가 붙어, IR자료로 잘못 분류된 증권사 리포트를 찾는 신호가 된다.
- **비교에 주는 영향.** 발행처가 빈 리포트는 비교에서 "같은 발행처"로 잡히지 않는다. 기술분석보고서는 작성기관이 달라도 같은 발행처(`한국IR협의회`)다.
- **사전을 고친 뒤.** 이미 분류된 행에는 저절로 반영되지 않는다. `tag requeue`로 해당 행을 대기 줄에 되돌리고 평소 백필로 다시 분류한다. 사람이 승인한(`verified`) 행은 되돌리지 않으므로 사전에서 바뀌거나 빠진 옛 이름을 그대로 가진다. 백필이 도는 동안에는 사전을 고치지 않는다(AI 요청이 바뀐다).

## 종목표와 버전

- 종목표 CSV의 머리줄은 칸 안 줄바꿈을 지운 뒤 정확히 `종목코드, 종목명, 시장, 산업명(대), 산업명(중), 주요제품`이어야 한다. 칸이 6개 미만인 행은 건너뛰고, 칸 앞뒤 공백은 지우고, 7번째 칸부터는 무시한다.
- **버전 정보 파일.** CSV와 같은 폴더의 `<CSV 이름에서 확장자 뺀 것>.version.json` = `{"version": "KRX@YYYY-MM-DD", "content_hash": "<64자리 소문자 16진수>"}`. 날짜는 종목표 **자료 기준일**이다. 함께 들어 있는 종목표의 버전은 `KRX@2026-05-08`이다.
- **내용 지문.** UTF-8로 읽고 맨 앞 BOM을 뺀다 → CSV로 해석한다 → 머리줄 칸은 안의 `\r`·`\n`을 모두 지우고, 나머지 칸은 안의 `\r\n`·`\r`을 `\n`으로 바꾸고, 모든 칸의 앞뒤 공백을 지운다 → 칸을 `\x1f`로, 행을 `\n`으로 잇는다 → UTF-8 바이트의 SHA-256. 줄바꿈 방식(LF/CRLF)과 따옴표 표기가 달라도 같은 지문이고, 칸 값이나 행 순서가 하나라도 바뀌면 다른 지문이다.
- **분류 명령(`tag run`, `tag escalate`, `--dry-run` 포함)이 시작할 때.** 버전 정보 파일이 없거나 지문이 다르면 행을 가져가기 전에 종료 코드 4로 멈추고 `stocks set-version` 실행을 안내한다. `tag inspect`·`tag reset-worker`는 종목표를 읽지 않으므로 확인하지 않는다.
- **저장 값.** 분류 결과의 `taxonomy_version`은 버전 정보 파일의 `version` 값이다. 파일 수정 시각은 쓰지 않는다. 분류된 행의 `taxonomy_version`은 그 행을 분류할 때의 버전 정보 파일 값이고, 분류 전(`pending`) 행은 비어 있다. 2026-10-09에 예전 표시 세 가지를 `KRX@2026-05-08` 하나로 통일했으므로, 다음 `stocks set-version` 전까지 분류된 행의 표시는 모두 `KRX@2026-05-08`이다. 같은 내용의 종목표에 다른 표시가 붙으면 안 되고, 이미 저장된 행의 표시를 손으로 바꾸지 않는다.
- **웹앱.** 지문이 다르거나 버전 정보가 없으면 경고 로그만 남기고 그대로 쓴다. 웹앱은 종목표를 목록·이름 표시에만 쓰고 버전 값을 저장하지 않는다. 종목표 파일을 아예 읽지 못하면 종목표를 쓰는 주소만 "사용 불가"가 된다: 기업 목록(`/api/workspace`, 관심 기업 켜기·끄기), 기업별 리포트 목록(`/api/stocks/{code}/reports`), 커버리지의 시장 집계(`/api/market`). 리포트 PDF·분석 실행·비교·기업 활동(`/api/stocks/{code}/activity`)·검토는 계속 동작한다.
- **버전 갱신(`stocks set-version --as-of YYYY-MM-DD`).** 날짜 형식 확인 → 머리줄 확인 → 지문 계산 → 버전 정보 파일을 원자적으로 교체. 어느 단계든 실패하면 파일은 그대로다. 같은 기준일을 다시 쓰는 것은 허용한다(이름이 "자료 기준일"이라서).
- **종목표가 오래됐을 때.** 이후 상장한 종목의 단일종목 리포트는 매칭되지 않아 `review_needed`(`krx_unmatched_in_scope`)로 쌓인다. 종목표를 새로 바꿔도 이미 쌓인 행은 저절로 풀리지 않는다. `tag requeue --krx-unmatched`(대기 줄로 되돌린 뒤 백필), `tag escalate --since <시각>`, 검토의 재분류 중 하나로 다시 분류해야 한다.
- **과거 데이터에 쓸 때.** 오늘의 종목표를 과거 전체에 그대로 적용하면 안 된다(그 시점에 없던 상장·폐지가 섞인다).

## 수집

- **일반 실행.** `reports`와 `failed_attempts`를 합친 가장 큰 메시지 번호의 다음부터 가져온다. 첫 실행이면 `INITIAL_CUTOFF_DAYS`(기본 30일)만큼 거슬러 간다. 그래서 중간에 빈 번호는 일반 실행으로 채워지지 않는다.
- **N일 되감기(`--backfill-days N`).** N일 전부터 훑으며 이미 있는 번호는 건너뛴다. 빈 번호를 채우는 유일한 방법이다. `--cutoff-days`와 함께 쓸 수 없다.
- **미리 보기(`--dry-run`).** 무엇을 받을지만 보여 주고 아무것도 쓰지 않는다. 텔레그램에는 접속한다.
- **실패 기록(`failed_attempts`).** 받지 못한 메시지마다 한 행(시도 횟수, 마지막 오류). 다음 수집 때 새 메시지보다 먼저 다시 시도하고, 성공하면 지운다. 메시지가 사라졌거나 PDF가 아니면 정리한다. 10회 이상이면 경고 로그를 남긴다(자동 차단은 없다) — 사람이 오류 메시지를 보고, 고칠 수 없는 메시지면 그 실패 기록 행을 지워 재시도를 멈춘다. 단 그 번호가 남은 행들(`reports` ∪ `failed_attempts`)의 가장 큰 번호보다 크면, 다음 일반 실행의 "가장 큰 번호 다음부터" 범위에 다시 들어와 또 시도된다.
- **PDF 파일.** 이름은 `<메시지번호>_<정리한 원래 이름>`. 임시 파일에 쓴 뒤 교체하고, SHA-256과 크기를 저장한다.
- **채널.** DB의 채널 라벨은 `TELEGRAM_CHANNEL`이다. `TELEGRAM_CHANNEL_ID`가 있으면 텔레그램 조회에만 그 숫자 ID를 쓴다.
- **종료 코드.** 0 성공(할 일 없음 포함), 1 전체 실패(설정 누락·인증·네트워크·예외), 2 일부 실패(이번 실행에서 실패 기록이 생김).

## 리포트 1건 재무 분석

- 단일종목(`report_type = '단일종목'`) 리포트만 분석한다. 종류가 비어 있어도 거절한다. 리포트당 결과 하나이고, 다시 분석하면 덮어쓴다(비교 칸은 비워진다). 화면에는 현재 버전(`PHASE2_SUMMARY_VERSION`, 기본 `llm-summary@1.0`)의 결과만 보인다.
- **다시 분석과 지우기.** 리포트 상세의 "다시 분석"(재무 상세가 있는 결과)은 저장 결과 재사용만 건너뛰고(`POST …/analyze?force=true`) 나머지 순서·오류가 같다. 새 결과가 저장될 때만 바뀌고, 어느 단계에서 실패해도 기존 결과와 다른 리포트의 해석문은 그대로다. "분석 결과 지우기"(`DELETE /api/reports/{rid}/analysis`)는 그 리포트의 결과 행을 지운다(버전 무관, 결과가 없어도 정상, 리포트 종류 무관, 모델 키 불필요). 둘 다 화면에서 한 번 더 묻고 한 건씩만 한다. 여러 건 분석은 다시 분석하지 않는다(저장 결과 재사용). 지운 결과는 보관하지 않는다.
- **다른 리포트의 해석문 비우기.** 리포트 X의 분석 결과가 새로 저장될 때(처음 분석, 옛 결과 덮어쓰기, 여러 건 분석, 다시 분석 모두)와 지워질 때, X를 앞 문서로 삼은 다른 리포트의 비교 해석문(비교 칸 네 개)을 비운다. 저장·삭제 직전에 비운다. 저장·삭제가 DB 오류로 실패해도 비운 것은 되돌리지 않는다(저장·삭제가 서로 다른 REST 호출이라, 비우기를 뒤에 두면 비우기만 실패했을 때 바뀐 결과를 기준으로 한 옛 해석문이 표시 없이 남는다). 묻는 것은 다시 분석·지우기 버튼뿐이다.
- **겹치지 않게.** 한 리포트에서 분석·지우기·비교 해석문 만들기는 동시에 하나만 돈다. 분석·지우기 쪽은 409 `이 보고서는 분석 중입니다. 잠시 후 새로고침해 주세요.`, 해석문 만들기 쪽은 409 `선택한 보고서를 분석하거나 지우는 중입니다. 잠시 후 다시 시도해 주세요.` 해석문은 두 리포트를 표시한 뒤 읽은 분석 결과로 만든다.
- 사용자가 고른 리포트만 분석한다. 목록을 보거나 선택만 해서는 분석하지 않는다.
- **확인 순서.** 행 확인(분석 대상 행이 없으면 404) → 같은 리포트가 바쁘면 409 → 단일종목이 아니면 422 → 재무 상세(`financial_details`)가 이미 있는 결과가 있으면(다시 분석이 아니면) AI를 부르지 않고 그 결과를 돌려준다(`analysis_reused: true`) → 모델 키·codex CLI 확인 → PDF 찾기 → 모든 쪽 글자 읽기(못 열거나 0쪽이면 422) → 글자 분석/그림 분석 판정 → AI 호출 → (그림 분석) 빈 결과면 422 → 다른 리포트의 해석문 비우기 → 저장. 모델 키가 없어도 재사용·목록·422 응답은 정상이다.
- **글자 없는 PDF 판정.** 모든 쪽의 글자로 문서 전체를 한 번 정한다. 쪽당 한글(`가`~`힣`) 평균이 50자 미만이고 영문 글자 평균이 300자 미만이면 그림 분석, 아니면 글자 분석이다(딱 같으면 글자 분석). 쪽마다 따로 정하지 않는다. 영어로 쓴 리포트는 글자 분석으로 간다. 기준값은 조정할 수 있는 상수다(실측: 본문이 빠진 PDF는 쪽당 한글 0~38자, 글이 짧아도 정상인 PDF는 76자 이상, 보통 리포트는 200자 이상).
- **그림 분석.** 1쪽부터 최대 20쪽을 그림(120dpi, 크기 한도를 넘으면 낮춤)으로 그려 AI에게 보여 준다. 시스템 프롬프트·응답 모양은 글자 분석과 같다. 분석 모델이 그림을 받지 못하거나 한 쪽도 그리지 못하면 AI 없이 422 `PDF에서 읽을 수 있는 텍스트가 없습니다.` 숫자 근거 확인은 하지 않고(대조할 원문 글자가 없다) 화면에 `그림으로 읽음 · 숫자 원문 대조 안 됨`을 보여 준다. 추출 신뢰도는 최대 `medium`. 호출 시간 한도는 `PHASE2_IMAGE_TIMEOUT_S`(기본 360초)이고 시간 초과는 다시 시도하지 않는다(다른 일시 오류는 한 번). 20쪽을 넘거나 못 그린 쪽이 있으면 `input_truncated = true`다.
- **빈 그림 결과.** 그림 분석의 답이 목표주가 없음·투자의견 `N/A`·재무 지표 0개·신뢰도 `low`를 모두 만족하면 저장하지 않고 422 `그림으로도 리포트 내용을 읽지 못했습니다.` 하나라도 어긋나면 저장한다. 글자 분석에는 이 규칙이 없다.
- **입력(글자 분석).** PDF 전체 쪽을 쪽마다 `--- Page N ---\n<글자>\n` 형식으로 넣는다. 글자 수 ÷ 3을 토큰으로 어림해 `PHASE2_MAX_INPUT_TOKENS`(기본 30000)를 넘는 쪽부터는 넣지 않고, 결과에 `input_truncated = true`를 저장한다. 글자 안에 잘렸다는 표시는 넣지 않는다.
- **숫자 근거 확인(글자 분석).** 지표마다 인용문과 그 쪽(위 쪽 표시로 나눈 글자)에 그 숫자가 실제로 있어야 한다. 없는 숫자는 결과에서 빼고, 뺀 개수를 `unsupported_numeric_values`로 저장한다. 빈 숫자는 빈 채로 둔다. 이 확인은 표의 열 맞춤까지 보장하지 않는다.
- **목표주가 방향.** 새·옛 목표주가가 둘 다 있으면 산수로 다시 정한다(`상향`/`불변`/`하향`). 둘 다 없으면 `N/A`, 하나만 있으면 모델 판단을 유지한다.
- **저장 값.** 비교 칸은 비우고, `summary_version`, `llm_model`, 입력·출력 토큰 수, 입력 쪽수, 잘림 여부, 읽은 방식(`input_mode`: 글자 `text` / 그림 `page_image`, 마이그레이션 010)을 저장한다. 그림 분석이면 입력 쪽수는 보낸 그림 수다.
- 값 집합(DB 제약): 목표주가 방향 `상향·불변·하향·신규·N/A`, 투자의견 `매수·중립·매도·N/A`, 투자의견 방향 `유지·상향·하향·신규·N/A`, 추출 신뢰도 `high·medium·low`, 읽은 방식 `text·page_image`, 근거 쪽 번호는 1 이상.
- 웹 서버 전체에서 동시에 도는 AI 호출은 분석과 비교를 합쳐 최대 2개다.

## 두 보고서 비교

- **고르는 조건.** 두 리포트가 모두 분석 대상이고, 둘 다 단일종목이거나 종류가 비어 있고, 서로 다른 리포트이고, 종목 코드를 하나 이상 공유해야 한다. 어긋나면 422(각 문구는 웹 계약에 고정).
- **순서.** `published_at`(같으면 `id`) 오름차순으로 앞 문서·뒷 문서를 정한다. 요청의 left/right 순서와 상관없다.
- **같은 발행처.** 두 발행처가 모두 있고 같을 때만 같은 발행처(`same_publisher`)다. 하나라도 비면 다른 발행처로 본다 — 화면은 "견해 차이"로 보여 준다.
- **수치 비교.** 지표·기간·단위·통화·회계 기준(연결/별도)·값 종류·시나리오가 모두 같고, 양쪽에 그 조합이 정확히 하나씩만 있을 때만 비교한다. 실적(actual)은 비교하지 않는다. 추정치와 가이던스는 비교한다. 같은 조합이 한쪽에 둘 이상이면 비교하지 않는다(어느 것인지 모르므로). %인 지표는 %p 차이로 계산한다. 0이나 음수가 끼면 증감률을 계산하지 않고 흑자 전환·적자 전환 같은 표시를 쓴다.
- **목표주가 변화.** 두 문서 각각의 새 목표주가(`target_price_new`)끼리만 계산한다. 리포트 안에 적힌 "이전 목표주가"는 쓰지 않는다.
- **비교 해석문.** 버튼(`POST /api/compare/analyze`)으로만 만든다. 결과는 뒷 문서의 분석 결과에 `prev_report_id`(앞 문서), `prev_match_type`(`same_publisher`/`cross_publisher`), `diff_narrative`, `comparison_details{metrics, previous_publisher, previous_published_at}`로 저장한다. 뒷 문서의 `prev_report_id`가 지금 고른 앞 문서일 때만 해석문을 보여 준다. 같은 짝의 해석문이 이미 있으면 AI를 부르지 않고 그것을 돌려준다. 뒷 문서 하나에는 해석문이 하나만 남는다 — 다른 짝으로 만들면 덮어쓰고, 뒷 문서를 다시 분석하거나 지우면 사라지고, 앞 문서의 결과가 새로 저장되거나 지워져도 비워진다. 두 문서 중 분석 결과가 없는 것이 있으면 422. 해석문을 만드는 동안 두 리포트의 분석·지우기는 409이고, 둘 중 하나가 분석·지우기 중이면 해석문 만들기가 409다.
- 그림으로 읽은 분석 결과끼리도 비교한다. 화면은 그림으로 읽은 쪽에 `그림으로 읽음 · 숫자 원문 대조 안 됨`을 보여 준다.
- 비교는 이미 저장된 분석끼리만 하는, 수집 표본 안의 비교다. 시장 전체 합의(컨센서스)라고 부르지 않는다.

## 커버리지

- **세는 것.** 기간별(일·주·월) 산업(대·중)·제품별 발행 건수, 종목별 다뤄진 횟수(순위), 리포트 종류별 발행량, 기업별 발행 추이와 발행처 비중.
- **날짜.** 집계 날짜는 `published_at`, 없으면 `sent_at`을 한국 시간 날짜로 바꾼 값이다. 분석 대상 외 행은 `published_at`이 비어 있으므로 보낸 시각의 한국 날짜로 센다. 기간 시작은 오늘(한국 시간) − `days`일.
- **분석 대상 외 포함(`include_oos`).** 켜면 리포트 종류별 발행량에 분석 대상 외 행도 들어간다. 산업·제품·순위 집계는 분석 대상만 센다.
- **기업 활동(`/api/stocks/{code}/activity`).** 그 코드를 `stock_codes`에 담은 분석 대상 행을 리포트 종류와 상관없이 모두 센다. 분류기가 산업·전략·시황 리포트에는 종목을 매핑하지 않으므로, 실제로 잡히는 것은 단일종목·섹터·기타 리포트다.
- **뜻.** "이 채널에서 다뤄진 횟수"다. 시장의 관심도 지표로 부르지 않는다.
- **반영 시점.** 검토 처리(승인·제외·재분류)나 되돌리기가 성공하면 바로 다음 요청부터 숫자에 반영된다. 그 밖의 변화(새 분류 결과)는 최대 180초 늦게 반영된다.

## 검토

- `review_needed` 행을 `tagged_at`이 오래된 순으로 하나씩 보여 준다. 다음 행을 고를 때 건너뛴 행은 빼지만, 남은 수는 건너뛴 행까지 포함한 `review_needed` 전체의 정확한 개수다. 건너뛰기는 브라우저 세션에서만 유지된다(서버에 남지 않음).
- **처리.** 승인 → `verified`. 제외 → `verified` + 분석 대상 외 행 모양 + 사유(사유 없으면 422). 재분류 → 분류 칸 전부를 비우고 `pending`(다음 `tag run`이 다시 분류). 재분류의 되돌리는 모양은 `tag requeue`와 같은 한 정의다.
- 처리 전 상태가 `review_needed`가 아니면 거절한다(409). 쓰기도 읽은 뒤 상태가 그대로일 때만 한다 — 그 사이 바뀌었으면 409.
- **되돌리기.** 서버 메모리에 처리 전후 스냅샷을 남긴다(최대 100개, 오래된 것부터 버림, 서버를 다시 켜면 모두 사라짐). 현재 행이 "처리 후" 스냅샷과 같을 때만 "처리 전"으로 되돌린다. 쓰기는 `tagging_status`·`tagged_at`·`tagging_locked_at`·`tagging_worker_id`가 그대로일 때만 한다. 그 사이 분류기나 다른 처리가 행을 바꿨으면 거절한다(409). 한 번 쓴 되돌리기 토큰은 다시 쓸 수 없다.

## 관심 기업

- 종목 코드 목록 하나(`{"stocks": [...]}`)다. 추가는 중복 없이 순서를 유지하고, 이미 있으면 아무것도 하지 않는다. 삭제는 없으면 아무것도 하지 않는다.
- 켜기·끄기 모두 먼저 받은 코드를 6자리로 채워 종목표에서 찾는다. 없으면 404. 그래서 종목표에서 사라진 종목은 관심 기업에서 뺄 수도 없다.
- 저장은 받은 코드 그대로다(채운 값이 아니다).
- 파일이 깨졌거나 모양이 틀리면 `.json.bak`으로 옮기고 빈 목록으로 본다.

## 리포트 수 (유사 기업 화면)

- **기준 행.** 분석 대상 행 중 `stock_codes`에 그 종목이 있고, 유효 날짜(`published_at`, 없으면 `sent_at`의 한국 날짜)가 오늘(한국) − 365일 이후(그날 포함)인 행. 종목 코드는 받은 그대로 비교한다(앞에 0을 채우지 않는다).
- **세 숫자.** 한 행은 그 종목에 대해 아래 셋 중 많아야 하나에 들어간다.

| 숫자 | 조건 |
|---|---|
| 종목 리포트(`stock_reports`) | 발행처 종류가 `broker`이거나 비어 있음, 리포트 종류가 `단일종목`·`기타`·비어 있음 중 하나, `stock_codes`가 정확히 `[그 종목]` |
| 섹터 언급(`sector_mentions`) | 발행처 종류가 `broker`이거나 비어 있음, 리포트 종류 `섹터`(매핑된 종목 수와 상관없음 — 한 종목만 매핑된 섹터 리포트도 종목 리포트가 아니다) |
| 기타 리서치(`other_research`) | 발행처 종류가 `data_provider`·`ir_agency`·`other`(리포트 종류·종목 수와 상관없음) |

  - 어느 조건에도 맞지 않는 행은 세지 않는다. 증권사가 여러 종목을 매핑한 단일종목·기타 리포트가 그 예다.
  - 발행처 종류가 빈 행은 증권사로 친다. 증권사 리포트가 있는 회사를 "리포트 없음"으로 잘못 띄우는 것이 반대 오류보다 더 해롭기 때문이다.
- **함께 주는 값.** 종목 리포트 중 가장 늦은 유효 날짜(`last_stock_report_date`), 종목 리포트를 낸 서로 다른 발행처 수(`brokers`, 빈 발행처는 세지 않음).
- **라벨.** `none`(리포트 없음): 종목 리포트 0건. `covered`(있음): 3건 이상이고 마지막 종목 리포트가 오늘 − 180일 이후(그날 포함). `few`(적음): 그 밖(1~2건, 또는 3건 이상인데 마지막이 180일보다 오래됨).
- 행이 없는 종목도 0·`none`으로 답한다. 텔레그램 수집이나 분류가 밀리면 최근 리포트가 빠져 숫자가 낮게 나온다.

## 주가 스냅샷

- **대상.** 종목표의 모든 종목(코드가 숫자·영문 대문자 6자리인 것, 같은 코드가 여러 행이면 마지막 행), 종목표 순서. 시장은 종목표의 `시장`으로 정한다: `KOSPI` → KOSPI, `KOSDAQ`·`KOSDAQ GLOBAL` → KOSDAQ, 그 밖 → 시장 없음(초과수익률 없음).
- **종목마다.** 오늘(한국)부터 380일(달력) 전까지의 수정주가 일봉(100행씩 세 번)과 현재가를 받는다. 종가가 0보다 큰 날만 쓰고, 같은 날이 겹치면 하나만 쓴다.
  - `as_of`: 받은 마지막 거래일. `close`: 그날의 수정 종가.
  - `ret_1w`·`ret_1m`·`ret_3m`·`ret_6m`: 마지막 종가를 5·21·63·126거래일 전 종가와 비교한 수익률(%). 종가가 그 거래일 수 + 1개보다 적으면 그 기간은 비우고 `short_history` 표시를 붙인다.
  - `avg_value_20d`: 마지막 20거래일 거래대금의 평균(빈 값은 빼고, 원 단위 반올림). 값이 하나도 없으면 비운다.
  - `market_cap`: 현재가의 시가총액(원).
  - `traded`: 거래정지면 false이고 `halted` 표시. 관리종목 등은 `admin_issue` 표시만 붙인다(거래 중으로 본다).
- **초과수익률** `xret_*` = 그 기간 수익률 − 같은 실행에서 받은 같은 시장 종목들의 그 기간 수익률 중앙값. 그 기간 수익률이 없는 종목은 중앙값에서 뺀다. 시장이 없거나 둘 중 하나가 비면 비운다.
- **실행 상태.** 받지 못한 종목 = KIS 오류, 이상한 응답, 쓸 만한 일봉 없음.

| 상태 | 조건 | 스냅샷 |
|---|---|---|
| `ok` | 받지 못한 종목 0 | 받은 종목을 저장(스냅샷과 수정 종가 이력) |
| `partial` | 받지 못한 종목이 전체의 20% 이하(정확히 20%도 partial) | 받은 종목을 저장(스냅샷과 수정 종가 이력). 받지 못한 종목은 이전 값을 그대로 두고 `no_data` 표시를 더한다(저장된 행이 없던 종목은 아무것도 생기지 않는다). 이력도 그대로 둔다 |
| `failed` | 20% 초과 | 하나도 바꾸지 않는다(이력도) |

  - 받지 못한 종목이 20%를 넘는 순간 그 실행은 `failed`로 정해지고 남은 종목은 KIS에 묻지 않는다.
  - KIS 접근 토큰을 못 받으면 아무 종목도 묻지 않고 그 실행은 `failed`다(모든 종목을 실패로 센다).
  - 실행 중 오류나 Ctrl+C면 실행 기록을 `failed`로 닫는다. 저장은 원자적이지 않아서, 저장 도중 끊기면 이미 쓴 종목은 새 값으로 남는다. 다음 실행이 모두 다시 쓴다.
- **실행 기록.** 실행마다 한 행: 시작·끝 시각, 상태(`running`으로 시작), 기준일(받은 종목 중 가장 늦은 `as_of`), 전체·성공·실패 종목 수, 메시지(`partial`·`failed`면 결과 설명, 받지 못한 종목 앞 20개, 첫 실패 이유). "가장 최근 실행"은 시작 시각이 가장 늦은 것(같으면 번호가 큰 것)이다.
- **수정 종가 이력(`stock_price_daily`).** `ok`·`partial` 실행이 받은 종목의 수정 종가를 (종목, 날짜)마다 한 행씩 쓴다. KIS가 준 수정주가 그대로이고 직접 보정하지 않는다. 수급 탭의 주가선에만 쓴다.
  - 이번 실행 전 스냅샷의 기준일과 이번 시계열의 첫날, 두 날의 저장된 종가가 이번에 받은 값과 같으면 그 기준일 다음 날들만 더한다.
  - 아니면 그 종목의 이번 시계열(380일) 전체를 다시 쓴다: 이력이 없음, 더 짧음(첫날 행이 없음), 지난 기준일 전에 끊김, 저장된 종가가 다름. 액면분할·병합·무상증자는 그 전의 모든 수정 종가를 바꾸므로 시계열 첫날 값에 드러난다(KIS가 하루 늦게 고쳐도 다음 실행에서 잡힌다).
  - 받지 못한 종목의 이력은 그대로 둔다. 실행마다 380일보다 오래된 이력을 모든 종목에서 지운다(종목표에서 빠진 종목 포함).
  - 수익률은 이력에서 계산하지 않는다. 지금처럼 실행마다 KIS 시계열로 다시 계산한다.
- **확인 실행(`--codes`).** 그 종목만 받아 계산 결과를 출력하고 스냅샷·실행 기록·이력에 아무것도 쓰지 않는다(상태 줄에 영향 없음). 초과수익률은 저장된 스냅샷 전체로 구한 시장 중앙값으로 계산하고, 저장된 스냅샷이 없으면 비운다. 종목표에 없는 코드는 묻지 않고 못 받은 것으로 센다.

## 반응 판정 ("덜 오름")

- 기간은 1주(5거래일)·1개월(21)·3개월(63) 중 화면에서 고른다. 기본은 1개월.
- 시드의 그 기간 초과수익률 `xs`가 +10%p 이상일 때만 판정한다. 10%p는 사용자가 정한 값이다.
- 피어마다 ρ = 피어 초과수익률 ÷ `xs`: ρ < 0.25 → `none`(미반응), 0.25 ≤ ρ < 0.6 → `partial`(부분반응), ρ ≥ 0.6 → `reacted`(반응).
- `undetermined`(판단 불가): 시드를 판정하지 않음(`xs` < 10%p이거나 없음), 피어 스냅샷이 없음, 피어가 거래 중이 아님(`traded`가 true가 아니거나 `halted`·`no_data` 표시가 있음), 피어의 그 기간 초과수익률이 없음, 시드와 피어의 `as_of`가 다름.
- 단순 수익률과 초과수익률은 판정과 상관없이 늘 함께 보여 준다.

## 후보

피어가 여섯 조건을 모두 만족하면 후보다(조건은 사용자가 정한 것이다). 만족하지 못한 조건마다 이유 코드를 이 순서로 붙인다.

| 조건 | 못 만족할 때의 코드 |
|---|---|
| 종목 리포트 0건(라벨 `none`) | `has_reports` |
| 반응이 `none` 또는 `partial` | `reacted`(반응) / `undetermined`(판단 불가) |
| 거래 중: 스냅샷이 있고 `traded`가 true이며 `halted`·`no_data` 표시가 없음 | `not_traded` |
| 20일 평균 거래대금 5억 원 이상 | `low_liquidity` |
| 지주회사가 아님(프로필의 `is_holding`) | `holding` |
| 행 등급이 `related` 이상 | `weak_similarity` |

- 값을 모르면 그 조건은 만족하지 못한 것이다: 스냅샷이 없으면 `not_traded`·`low_liquidity`, 리포트 수 라벨이 없으면 `has_reports`. 애매하면 후보로 띄우지 않는다.
- 화면은 목록 전체를 보여 주고 필터는 모두 꺼 둔다. 후보 행은 강조하고, 후보가 아닌 행은 이유를 흐리게 보여 준다. 지주사·금융사·정보 부족·관리종목 표시는 붙이되 숨기지 않는다.

## 유사 기업

### 대상 회사와 사업보고서
- 회계연도 N의 사업보고서: MongoDB 문서 중 `is_final = true`, `fiscal_year = N`, `parser_version` 0.2.0 이상. 회사(`stock_code`)마다 보고서 하나 — 결산일(`fiscal_end`)이 가장 늦은 것, 같으면 접수일·접수번호가 늦은 것. 12월 결산이 아닌 회사도 같다(2025-03-31 결산 보고서는 N = 2025).
- 대상 회사: 코스피(`corp_cls` Y)·코스닥(K)이고, 앱 종목표에 있고, 종목표 `산업명(중)`이 `리츠`가 아니고, DART 회사명과 종목표 이름 어디에도 `스팩`·`기업인수목적`·`부동산투자회사`가 없는 회사. 코넥스·기타 법인은 대상이 아니다. 이름의 `리츠`로는 빼지 않는다(`메리츠금융지주` 등이 잘못 빠진다). 대상이 아닌 회사에는 AI를 부르지 않는다.

### 프로필 (AI 사업 요약 카드)
- **입력 조립.** 블록마다 머리표를 붙여 이 순서로 잇고, 블록마다 상한에서 자른다. 빈 블록은 넣지 않는다. 숫자는 조정 가능한 기본값이고 프로필 버전에 묶인다.
  1. `[사업의 개요]` 020100 본문, 6,000자.
  2. `[주요 제품 및 서비스]` 020200 본문, 2,500자.
  3. `[주요 제품 표]` 020200 표 중 제품·부문 표만, 합계 2,500자. 남기는 표: 첫 행에 `품목`·`제품`·`부문`·`용도`·`상표` 중 하나가 있고, 두 행 이상이고, 단가 표시(`천/톤`, `원/`, `$/`, `단가`)가 없고, 숫자 칸이 70% 이하(빈 칸·대시 칸은 세지 않음)인 표.
  4. 사업의 개요가 800자 미만일 때만: `[기타 참고사항]` 020700 본문 3,000자, `[매출 및 수주]` 020400 본문 1,500자.
  5. 020800(영업의 현황) 섹션이 있으면 마지막에 `[영업의 현황]` 020800 본문과 표, 6,000자. 금융업 양식(020800은 있고 020200은 없음)이면 2·3을 넣지 않는다. 사업을 둘 겸영하는 회사(`(제조서비스업)`·`(금융업)`으로 절을 나눈 보고서, 020200과 020800이 둘 다 있음)는 2·3도 넣는다.
  - 전체는 12,000자에서 자른다. 하나라도 잘렸으면 `input_truncated`. 입력이 비면 AI를 부르지 않고 그 회사는 실패(`사업보고서 본문이 비어 있습니다`)다.
- **추출 규칙.** 회사가 직접 만들거나 파는 것과 이름이 있는 개발 제품만 적는다. 산업의 특성·시장 규모·성장성·경기 변동·정책 문단에서는 아무것도 가져오지 않는다. 추론하지 않는다(고객사·경쟁사는 원문에 이름이 있을 때만). 키워드는 구별력 있는 틈새 용어만(일반어 `반도체`·`제조`·`기술력`·`글로벌`·`친환경`·`수요` 금지, `AI`는 AI 제품을 팔 때만). 약어는 대문자 영문, 그 밖은 한국어 명사구. 틈새 업종과 요약에는 고객사·경쟁사·그룹 이름을 쓰지 않는다. 정보가 부족하면 빈 목록과 `info_quality = 부족`.
- **근거 검사.** 제품·키워드·고객사·경쟁사·부문 제품·부문 키워드마다, 그 말이나 동의어표의 다른 표기가 입력 글에 있어야 남긴다(대소문자·공백·가운뎃점·하이픈 무시). 근거율 = 남긴 말 수 ÷ AI가 낸 말 수(낸 말이 없으면 1). 근거율이 0.8 미만이면 재처리 모델로 한 번 더 추출하고, 그 결과(근거 검사 뒤)를 근거율과 상관없이 쓴다. 재추출 호출이 실패하면 첫 결과를 쓴다.
- **상한.** 검증 뒤 코드에서 자른다(같은 비교 열쇠는 하나만 남김): 제품 12, 키워드 15, 적용처 8, 고객사 8, 경쟁사 8, 부문 6(매출 비중 큰 순, 비중 미상은 뒤, 같으면 원래 순서), 부문 제품·키워드 각 6, 역할 2(하나도 없으면 `기타`), 틈새 업종 40자, 요약 160자. 이름 없는 부문은 버리고, 0~100 밖의 비중은 -1(비중 미상)로 바꾼다.
- **실패.** 회사 하나의 추출이 시간 한도 초과, AI 오류, 형식 오류(한 번 더 물어도 실패), 거부로 끝나면 그 회사를 `failed`와 이유로 남기고 다음 회사로 간다.
- **재사용.** 같은 (회계연도, 프로필 버전)에 `ok` 프로필이 있고 접수번호(`rcept_no`)와 파서 버전이 같으면 다시 만들지 않는다. 프로필 버전이 바뀌거나, 보고서가 바뀌거나(정정 등), 파서 버전이 바뀌거나, 이전이 실패였으면 다시 만든다.
- **실패해도 이전 프로필은 남는다.** 다시 추출하다 실패한 회사에 `ok` 프로필(이전 보고서·파서로 만든 것)이 있으면 그대로 두고 화면에도 계속 쓴다. 그 실행에서는 실패로 세고 `kept_previous`에 적는다. `ok` 프로필이 없던 회사만 `failed` 행이 된다.
- AI가 낸 표기를 그대로 저장한다. 고객사·경쟁사는 지금 화면에 쓰지 않지만 저장한다.

### 비교 열쇠와 동의어
- 열쇠: 용어 전체가 동의어표의 한 표기이면 그 항목의 표준 표기로 바꾼다. 아니면 용어를 공백·가운뎃점·하이픈·빗금으로 나눈 낱말마다, 낱말 전체가 한 표기일 때만 표준 표기로 바꾼다. 그다음 대소문자를 무시하고 공백·가운뎃점·하이픈을 지운다. 낱말 안의 일부는 바꾸지 않는다(`시디램프`는 DRAM이 아니다). 예: `Legacy DRAM`, `legacy-dram`, `Legacy 디램`은 모두 `legacydram`.
- 공통 키워드·용어표·테마 검색의 용어 일치는 이 열쇠로 비교한다. 화면 표기는 동의어표의 표준 표기, 없으면 그 빌드에서 처음 만난 원래 표기다.
- 동의어 정규화는 빌드 때 한다. 동의어표를 고쳐도 AI 추출을 다시 하지 않는다. 한 표기는 표준 하나에만 속해야 한다.

### 임베딩과 유사도
- 회사 임베딩 글: `업종: {틈새 업종}` / `요약: …` / `제품: …` / `키워드: …` / `사업부문: {이름}({비중}%): {제품}; …` / `적용처: …`(줄마다). 비중 미상이면 `({비중}%)`를 뺀다. 고객사·경쟁사·그룹 이름은 넣지 않는다 — 같은 고객이나 같은 그룹이라서 비슷해 보이면 안 된다.
- 부문 임베딩 글: `{틈새 업종} — {부문 이름}: {부문 제품} / {부문 키워드}`, 부문마다 하나.
- 임베딩은 1536차원이고 길이 1로 맞춘다. 회사 유사도 = 두 회사 임베딩의 코사인. 부문 유사도 = 시드에서 고른 부문과 다른 회사의 각 부문 사이의 코사인이고, 회사마다 가장 높은 부문 하나(같으면 번호가 작은 부문)가 그 회사의 "겹치는 부문"이다. 겹치는 부문의 매출 비중이 노출도다(-1이면 "비중 미상").
- 시드 부문 순서: 매출 비중 큰 순, 비중 미상은 뒤, 같으면 부문 번호 순. 첫 번째가 기본 선택이다. 부문이 없는 시드는 부문 쪽을 계산하지 않는다.

### 등급
- 공개 빌드마다 백분위표 두 개를 만든다: 회사 표(그 빌드의 모든 회사 쌍, 자기 자신 제외)와 부문 표(서로 다른 회사의 부문 쌍. 200만 쌍이 넘으면 고정된 무작위 표본 200만 쌍). 표는 `[[백분위, 코사인], …]`이고 백분위는 95.0~99.9(0.1 간격), 99.95, 99.99, 100이다.
- 유사도의 백분위는 표의 앞뒤 두 점 사이를 직선으로 보간해 구한다. 95 백분위 값보다 작으면 백분위가 없고(목록에 넣지 않는다), 100 값보다 크면 100이다. 같은 코사인에 점이 여럿이면 가장 높은 백분위를 쓴다.
- 등급: `very_high`(매우 유사) ≥ 99.5, `high`(유사) ≥ 98, `related`(관련) ≥ 95. 피어의 행 등급 = 회사 등급과 부문 등급 중 높은 것.

### 피어 목록 (요청할 때 계산)
1. 회사 유사도 상위 100곳, 그리고 시드에서 고른 부문으로 잰 부문 유사도 상위 100곳(회사마다 가장 가까운 부문 하나). 각각 가까운 순 200행에서 시드 자신과 지금 종목표에 없는 회사(상장폐지 등)를 뺀 뒤 자른다.
2. 회사 단위로 합치고, 그 빌드에 `ok` 프로필이 없는 회사를 뺀다. 각 쪽은 자기 백분위표로 등급을 매기고 `related` 미만인 쪽은 없는 것으로 본다. 두 쪽 다 없으면 뺀다.
3. 순위: 두 백분위 중 큰 값이 높은 순, 같으면 작은 쪽 백분위, 회사 유사도, 부문 유사도, 종목코드 순. 상위 50곳.
- 공통 키워드: 시드와 피어의 비교 열쇠(키워드·제품·부문 키워드·부문 제품) 중 둘 다 가진 것으로서 그 빌드 용어표에 있는 것. 그 열쇠를 가진 회사 수가 적은 순(같으면 열쇠 순)으로 최대 5개, 보유 회사 수와 함께 보여 준다. 없으면 빈 목록("설명 약함")이다.
- 같은 산업분류: 종목표 `산업명(중)`이 같으면 같음, 다르면 다름, 한쪽이 비면 모름.
- 순위에 공통 키워드 가산을 더하는 장치는 있지만 기본값 0(끔)이다.

### 테마 검색
- 질의는 공백을 하나로 줄이고 동의어 표기를 표준 표기로 바꾼 글을, 공개 빌드의 임베딩 모델로 임베딩한다(같은 모델·같은 글이면 서버 캐시 최근 256개).
- 세 순위를 RRF(점수 = Σ 1 ÷ (60 + 순위))로 합쳐 높은 순 상위 `limit`곳(점수가 같으면 종목코드 순):
  1. 질의 임베딩과 회사 임베딩이 가까운 상위 100곳.
  2. 질의 임베딩과 부문 임베딩이 가까운 상위 100곳(회사마다 가장 가까운 부문).
  3. 용어 일치. 질의 용어는 질의 전체와, 공백·쉼표·가운뎃점으로 나눈 2자 이상 조각 각각이다. 비교 열쇠가 프로필 용어의 열쇠와 완전히 같으면 일치다. 일치한 용어가 많은 순, 같으면 그 용어들의 보유 회사 수 합이 적은 순, 그다음 종목코드 순.
- 종목표에 있고 그 빌드에 `ok` 프로필이 있는 회사만 나온다. 시드가 없으므로 반응·후보 판정은 없다. 결과를 누르면 그 회사가 시드인 유사 기업 탭이 열린다.

### 빌드 수명

| 시작 → 결과 | 조건 |
|---|---|
| (시작) → `running` | 다른 `running` 빌드가 없거나, 있어도 마지막 진행이 6시간보다 오래됨(그 빌드를 `failed`로 바꾸고 시작) |
| 시작하지 않음 | 마지막 진행이 6시간 이내인 `running` 빌드가 있음(정확히 6시간이면 아직 진행 중으로 본다), 또는 분류 작업이 진행 중 |
| `running` → `done` | 시험 실행이 아니고, 프로필 성공(재사용 포함) ≥ 대상 회사의 95% |
| `running` → `incomplete` | 시험 실행이 아니고 95% 미만. 다시 실행하면 성공한 회사는 재사용하고 이어서 한다 |
| `running` → `pilot` | 시험 실행(`--pilot`) |
| `running` → `failed` | 대상 회사가 없음, 실행 중 오류, 중단(Ctrl+C) |

- 한 번에 빌드 하나만 돈다. 마지막 진행 시각은 회사 하나, 임베딩 묶음 하나가 끝날 때마다 바뀐다. `failed`로 바꾸지 못한 채 프로세스가 죽은 빌드는 6시간 규칙으로 정리된다.
- 화면은 `done` 빌드 중 끝 시각이 가장 늦은 것(같으면 번호가 큰 것)만 쓴다. `running`·`incomplete`·`pilot`·`failed`는 화면에 나오지 않는다.
- `done`일 때만 그 (회계연도, 프로필 버전)의 모든 `ok` 프로필의 용어 열을 다시 쓰고 용어표·백분위표를 기록한다. 시험 실행은 용어 열을 바꾸지 않고, 대상 회사마다 회사·부문 유사도 상위 10을 출력한다. 시험 실행의 프로필도 저장되어 다음 빌드가 재사용한다.
- 임베딩은 그 (회계연도, 프로필 버전)의 `ok` 프로필과 부문 중 이 빌드의 임베딩 모델로 만든 임베딩이 없는 것만 만든다. 다른 모델의 임베딩은 건드리지 않는다.
- 용어표·백분위표는 그 (회계연도, 프로필 버전)의 `ok` 프로필 전체로 계산한다. `--codes`·`--limit`로 대상을 줄인 실행도 같고, 대상 수는 줄인 그대로 기록된다.
- 보존: 빌드를 마친 뒤 공개 빌드는 끝 시각 순 최근 3개만 남긴다. 남긴 공개 빌드 중 가장 오래된 것보다 번호가 작은 `pilot`·`failed`·`incomplete` 빌드도 지운다. 공개 빌드가 하나도 없으면 어떤 빌드도 지우지 않고, `running` 빌드는 지우지 않는다. 그다음 남은 빌드와 지금 프로필 버전 어디에도 쓰이지 않는 프로필·부문·임베딩을 지운다. 정리가 실패해도 빌드 결과는 그대로다.

## 수급 순위

- **대상 종목.** 주가 갱신과 같다. 종목표에서 코드가 숫자·영문 대문자 6자리인 종목이고, 같은 코드가 여러 행이면 마지막 행이며, 종목표 순서로 다룬다. 시장 규칙도 주가와 같다.
- **거래일.** 한 종목의 거래일은 KIS가 그 종목에 돌려준 날 중 종가가 0보다 큰 날이다.
  - 거래정지일은 종가는 있고 순매수가 모두 0인 날로 온다. 거래일로 저장하고 창에도 넣는다.
  - 종가가 0이거나 빈 날은 상장 전 날을 0으로 채워 온 것이다. 저장하지 않는다.
- **주체 11개.** KRX 투자자 구분이다. 금액은 그 주체의 순매수 거래대금이고, KIS 단위 그대로 백만 원(KIS 반올림)이다. 표의 순서가 화면의 순서다.

| 키 | 이름 | KIS 필드 (순매수 거래대금, 백만 원) |
|---|---|---|
| `pe_fund` | 사모 | `pe_fund_ntby_tr_pbmn` |
| `foreigner` | 외국인 | `frgn_reg_ntby_pbmn` (KRX '외국인' = 등록 외국인. 기타외국인 `frgn_nreg`는 어느 주체에도 넣지 않는다) |
| `institution` | 기관합계 | `orgn_ntby_tr_pbmn` + `etc_orgt_ntby_tr_pbmn` |
| `pension` | 연기금 | `fund_ntby_tr_pbmn` + `etc_orgt_ntby_tr_pbmn` |
| `trust` | 투신 | `ivtr_ntby_tr_pbmn` |
| `fin_invest` | 금융투자 | `scrt_ntby_tr_pbmn` |
| `insurance` | 보험 | `insu_ntby_tr_pbmn` |
| `bank` | 은행 | `bank_ntby_tr_pbmn` |
| `other_fin` | 기타금융 | `mrbn_ntby_tr_pbmn` |
| `other_corp` | 기타법인 | `etc_corp_ntby_tr_pbmn` |
| `individual` | 개인 | `prsn_ntby_tr_pbmn` |

  - 항등식: 금융투자 + 보험 + 투신 + 사모 + 은행 + 기타금융 + 연기금 = 기관합계. 위 대응에서는 `scrt + insu + ivtr + pe_fund + bank + mrbn + fund = orgn`과 같다(`etc_orgt`는 양쪽에서 지워진다). 확인 실행(`--codes`)이 그 차이를 함께 낸다.
- **창과 이력 일수 N.** 날 D에서 한 종목의 창은 그 종목의 저장된 행 중 D 이하인 최근 250행이다(D 포함). N은 창의 행 수다.
- **250일 순위.** 주체마다 `1 + (창 안에서 그 주체 순매수가 D의 값보다 큰 날의 수)`.
  - 같은 값은 같은 순위이고, 더 큰 날만 센다. 1위가 가장 강하게 들어온 날이다.
  - 순매수가 0 이하인 날도 매긴다(수급 탭의 표에 보인다).
  - N < 60이면 순위가 없다. 60 ≤ N < 250이면 있는 기간으로 매기고 '이력 짧음(N일)'을 붙인다.
- **시총 대비 %.** 순매수(원) ÷ 그날 시가총액(원) × 100.
- **그날 시총은 받아 둔 실제 값만 쓴다.** 날 D의 시총은 주가 스냅샷의 기준일이 D와 같은 종목의 시가총액, 즉 그날 주가 갱신이 받은 값이다. 스냅샷 기준일이 D가 아니거나 스냅샷이 없는 종목은 그날 시총이 없다. 예전 시총을 쓰거나 주가로 거꾸로 계산하지 않는다(KIS에는 과거 날짜의 시총·상장주식수를 주는 API가 없다).
- **순위를 매길 날.** 수급 갱신이 `ok`·`partial`이면 그 실행의 기준 거래일(받은 가장 늦은 거래일) D 하루만 매긴다.
  - DB 함수 `rank_investor_flows`가 그날 행 중 시총이 있고 아직 매기지 않은 행에 그날 시총·N·11개 순위·매긴 시각을 쓴다.
  - 시총이 없는 종목의 행은 매기지 않은 채 남는다. 같은 날 주가를 다시 받은 뒤 수급 갱신을 다시 돌리면 그때 매긴다.
  - 순위가 있는 종목이 하나 이상이면 그날을 순위 매긴 날 목록에 넣는다(이미 있으면 종목 수만 고친다). 하나도 없으면 넣지 않는다.
  - 실행이 빠진 날(PC 꺼짐, 주가 갱신 실패)의 원자료는 다음 실행이 채운다. 하지만 그날 시총이 없어서 순위를 매기지 않고 날 목록에도 넣지 않는다. 수급 탭 그래프에는 그날도 보인다.
- **날 값 고정.** 한 번 매긴 행의 시총·N·순위는 다시 계산하지 않는다. 지난 날짜를 다시 보면 그날 매긴 그대로 보인다.
- **PC와 DB가 같은 계산.** DB 함수와 같은 규칙의 기준 계산이 PC 쪽에도 있고, 확인 실행이 이 계산을 쓴다. 둘은 같은 입력에 같은 순위를 내야 한다.

### 수집 (`flows update`)

- **기준일.** 한국 시간으로 평일 18:00 이후면 오늘, 아니면 오늘 이전의 가장 가까운 평일(월요일 아침·주말 → 금요일). 장중·장 직후의 잠정 자료를 저장하지 않으려는 규칙이다. 공휴일이면 KIS가 그 전 거래일까지를 준다.
- **시작 거절.** 가장 최근 주가 갱신이나 가장 최근 수급 갱신이 `running`이고 시작한 지 2시간이 안 됐으면 아무것도 바꾸지 않고 끝난다. 2시간보다 오래된 `running`은 죽은 실행으로 보고 무시한다. 확인 실행도 같은 확인을 한다(아무것도 쓰지 않지만 같은 앱키의 KIS 호출 한도를 나눠 쓰므로).
- **접근 토큰.** 주가 갱신과 같은 토큰 파일을 쓰고, 종목을 묻기 전에 한 번 받는다. 못 받으면 아무 종목도 묻지 않고 그 실행은 `failed`다(모든 종목을 실패로 센다).
- **거래일 달력.** 삼성전자(005930)를 가장 먼저 받아 최근 310거래일 달력을 만든다. 보관 범위와 빈 날 판정이 이 달력을 기준으로 한다.
  - 이번 실행의 KIS 응답으로만 만든다. 저장된 날로 만들면 그 사이의 구멍이 보이지 않기 때문이다. 그래서 실행마다 삼성전자를 11번 안팎 묻는다.
  - 삼성전자도 대상 종목 하나로 센다. 삼성전자를 못 받으면 다른 종목은 묻지 않고 그 실행은 `failed`다(모든 종목을 실패로 센다).
- **종목마다.** 기준일에서 끝나는 30거래일 묶음을 한 번 받는다. 보관 범위(달력의 최근 310거래일 = 250 창 + 60 다시 보기) 안에 저장되지 않은 거래일이 있으면 그 앞 묶음을 차례로 더 받는다. 처음 실행, 끊긴 첫 채우기, PC를 오래 꺼 둔 경우가 모두 이 규칙 하나로 채워진다.
  - 상장 전 날(종가 0·빈 값)을 만나면 그 종목의 자료 시작일로 기억한다. 그보다 앞은 다시 묻지 않는다.
  - KIS가 끝까지 돌려주지 않는 날이 있어도, 필요한 묶음을 다 받았으면 받은 그대로 저장한다. 그런 날이 보관 범위 안에 있는 동안은 실행마다 그 종목을 보관 범위 첫날까지 다시 묻는다.
  - 필요한 묶음을 모두 받으면 그 종목의 행을 한 번에 저장한다. 원자료 칸(`net_*`)과 받은 시각만 쓰고 순위·시총 칸은 건드리지 않는다. 같은 날을 다시 받으면 받은 값으로 덮어쓴다. 실행이 중간에 끊겨도 끝난 종목은 남고 다음 실행이 나머지를 받는다.
  - 묶음 하나라도 못 받으면(KIS 오류, 이상한 응답) 그 종목은 실패이고 이번 자료는 저장하지 않는다. 앞부분만 받은 짧은 창으로 순위가 매겨져 영영 틀리는 일을 막는다.
- **실행 상태.** 주가와 같은 규칙이다: 받지 못한 종목 0 → `ok`, 20% 이하(정확히 20%도) → `partial`, 20% 초과 → `failed`. 20%를 넘는 순간 남은 종목은 묻지 않는다.
- **`ok`·`partial`일 때만** 순위를 매기고(위 "순위를 매길 날") 오래된 자료를 정리한다. 원자료는 기준일로부터 470일(달력)보다 오래된 행을 지우되, 보관 범위 첫날 이후의 행은 지우지 않는다(평일 공휴일에도 예약 실행은 돌아 기준일만 앞으로 가고 거래일 달력은 그대로라, 긴 연휴 뒤에는 '기준일 − 470일'이 보관 범위 안으로 들어올 수 있다). 순위 매긴 날 목록은 최근 60개만 남긴다. `failed`면 순위도 정리도 하지 않는다. 받아 저장한 원자료는 남지만 화면에 새 날이 나오지 않는다.
- **실행 기록.** 실행마다 한 행: 시작·끝 시각, 상태(`running`으로 시작), 기준일(받은 가장 늦은 거래일), 전체·성공·실패 종목 수, 순위를 매긴 날 수(0 또는 1), 메시지(`partial`·`failed`면 결과 설명, 받지 못한 종목 앞 20개, 첫 실패 이유). 예외나 Ctrl+C면 `failed`로 닫는다. "가장 최근 실행"은 시작 시각이 가장 늦은 것(같으면 번호가 큰 것)이다.
- **확인 실행(`--codes`).** 그 종목들만 250거래일치를 받아(종목마다 9번 안팎) PC에서 같은 규칙으로 기준일의 순위를 계산해 JSON으로 낸다(기관합계 항등식 차이 포함). 원자료·실행 기록·순위·상태 줄에 아무것도 쓰지 않는다. 종목표에 없는 코드는 묻지 않고 못 받은 것으로 센다.

### 순위표 (수급 랭킹 화면)

- **그룹.** 고른 날의 행 중 다음을 모두 만족하는 종목이다: 고른 주체의 순매수 > 0, 그날 시총이 있고 하한 이상(기본 1,000억 원, 화면에서 바꾼다), 고른 주체의 250일 순위가 있음(N ≥ 60).
- **점수(백분위 평균).** 그룹 안에서 계산한다.
  - TS 점수 = `100 × (N − 순위) ÷ (N − 1)`. 1위가 100점, N위가 0점이다.
  - CS 점수 = `100 × (r − 1) ÷ (M − 1)`. r은 그룹의 시총 대비 %를 작은 쪽부터 줄 세운 등수(같은 값은 평균 등수), M은 그룹 종목 수다. M = 1이면 100이다.
  - 종합 점수 = (TS + CS) ÷ 2. 250일 1위여도 시총 대비가 그룹 하위권이면 중간쯤에 서고, 둘 다 높아야 맨 위에 온다. 하한이나 주체를 바꾸면 그룹이 바뀌어 CS가 다시 계산된다.
  - 비율과 점수는 정확한 분수로 계산하고 비교한다. 소수 반올림 잡음으로 같은 값의 순서가 바뀌지 않게 하려는 것이다. 응답에는 한 번 반올림한 소수로 준다.
- **정렬 네 가지.** 큰 순이고, 맨 끝은 종목코드 순이다. 기본은 `score`다.
  - `score` 종합 점수 → 시총 대비 % → 순매수 → 종목코드
  - `rank` TS 점수 → 시총 대비 % → 순매수 → 종목코드 (N이 250이면 250일 순위 순서와 같다)
  - `pct` 시총 대비 % → TS 점수 → 순매수 → 종목코드
  - `amount` 순매수 → 시총 대비 % → 종목코드
- **칸.** 순번, 종목코드·이름·시장, 시총(억 원), 순매수(억 원, 소수 한 자리), 시총 대비 %(소수 둘째 자리), 250일 순위(고른 주체. N < 250이면 '이력 짧음(N일)'), 종합 점수(소수 한 자리), 참고 순위(사모·외국인·기타법인의 250일 순위, 고른 주체와 상관없이 늘), 리포트 수(유사 기업 화면과 같은 정의, 최근 365일).
- **표시.** 순위 칸이 1~3위면 분홍으로 강조한다. 날짜는 순위 매긴 날 목록(최근 60개)에서 고르고 기본은 가장 최근이다. 처음 50줄을 보이고 '더 보기'로 50줄씩 최대 200줄까지 늘린다. 줄을 누르면 그 기업 화면(리포트 라이브러리)으로 간다. 하루 수급의 이후 주가 예측력은 약하다는 연구가 많아서, 화면의 '표 읽는 법'에 "매수 신호가 아니라 눈여겨볼 종목을 고르는 용도"라고 적는다.

### 기업 화면 수급 탭

- **위 표.** 주체 11개가 한 줄씩이고, 칸은 순매수(억 원), 시총 대비 %, 250일 순위(1~3위 분홍)다.
  - 기준은 그 종목의 최근 250행 중 순위를 매긴 가장 늦은 날이고, 그 날짜와 시총을 보인다.
  - N < 60이면 순위는 '—'이고 '상장 N거래일'을 보인다. 60 ≤ N < 250이면 '이력 짧음(N일)'을 보인다.
  - 줄을 누르면 아래 그래프의 주체가 바뀐다.
- **아래 그래프.** 고른 주체(기본 사모)의 일별 순매수 막대(순매수 빨강, 순매도 파랑), 기간 첫날부터 더한 누적 순매수 선, 수정 종가 선(오른쪽 축. 종가가 없는 날은 선을 끊는다). 기간은 1개월(21거래일)·3개월(63, 기본)·6개월(126)·1년(250)이고, 저장된 행이 그보다 적으면 있는 만큼 그린다.
- 저장된 행이 하나도 없으면 `이 종목은 수급 자료가 없습니다.` 안내 화면이다(신규 상장 등). 행은 있지만 순위를 매긴 날이 없으면 표의 값은 비우고 그래프만 보인다.

## 상태 줄 (자료 기준일)

- **주가가 밀림**(처음 맞는 이유 하나):
  1. 성공(`ok`·`partial`) 실행이 한 번도 없음 → `주가가 아직 한 번도 갱신되지 않았습니다`.
  2. 가장 최근 실행이 `failed`(기준일과 상관없이) → `마지막 주가 갱신이 실패했습니다`.
  3. 마지막 성공 실행의 기준일이 기대 거래일보다 이름 → `주가가 {M}월 {D}일 기준으로 밀려 있습니다. 휴장일이면 정상입니다`.
- **기대 거래일**: 한국 시간으로 지금이 평일 20:00 이후면 오늘, 아니면 오늘 이전의 가장 가까운 평일(월요일 아침 → 지난 금요일, 토·일 → 금요일). 매일 주가 갱신이 18:30에 시작하므로 끝난 뒤인 20:00을 기준으로 한다. 공휴일은 모른다.
- 가장 최근 실행이 `running`인 것은 그 자체로 밀림이 아니다(기준일로 판단한다). 기대 거래일보다 늦은 기준일(장중 손으로 돌린 실행)은 밀림이 아니다.
- **수급이 밀림**(주가와 같은 기대 거래일, 처음 맞는 이유 하나):
  1. 성공(`ok`·`partial`) 수급 실행이 한 번도 없음 → `수급 자료가 아직 한 번도 갱신되지 않았습니다`.
  2. 가장 최근 수급 실행이 `failed`(기준일과 상관없이) → `마지막 수급 갱신이 실패했습니다`.
  3. 마지막 성공 수급 실행의 기준일이 기대 거래일보다 이름 → `수급 자료가 {M}월 {D}일 기준으로 밀려 있습니다. 휴장일이면 정상입니다`.
  - `running`과 기대 거래일보다 늦은 기준일은 주가와 같이 다룬다. 주가 갱신이 실패해 수급을 건너뛴 날은 3번으로 보인다.
- **리포트가 밀림**: 분석 대상 리포트가 하나도 없거나, 가장 최근 `sent_at`이 지금보다 3일 넘게 이름(정확히 3일은 밀림이 아님, 미래 시각도 밀림이 아님). 분석 대상 기준이므로 수집은 되는데 분류가 밀려도 밀린 것으로 나온다.
